# Edgento API — Database Schema

Database: PostgreSQL 16
Migration Tool: Flyway (files in `src/main/resources/db/migration/`)
Naming: All table and column names use `snake_case`
Primary Keys: All PKs are UUID, generated by PostgreSQL's `gen_random_uuid()`
Timestamps: All use `TIMESTAMPTZ` (timezone-aware) — never plain `TIMESTAMP`

---

## Entity Relationship Diagram

```
leads
  │
  └──< audit_conversations   (one lead can have many conversations)
            │
            ├──< conversation_messages  (one conversation has many messages)
            │
            └──1 audit_reports          (one conversation has at most one report)
```

## Table: `leads`

Stores every person who has interacted with Edgento (via contact form or AI agent).

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `UUID` | `PK, DEFAULT gen_random_uuid()` | Globally unique identifier |
| `name` | `VARCHAR(255)` | `NOT NULL` | Full name of the lead |
| `email` | `VARCHAR(255)` | `NOT NULL` | Email address |
| `company_name` | `VARCHAR(255)` | nullable | Company or business name |
| `phone` | `VARCHAR(50)` | nullable | Phone number |
| `source_page` | `VARCHAR(100)` | nullable | URL path where lead was captured (e.g. `/services`) |
| `utm_source` | `VARCHAR(100)` | nullable | Marketing attribution (e.g. `google`, `linkedin`) |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL, DEFAULT NOW()` | When the lead was captured |

**Indexes:**
- `idx_leads_email` on `(email)` — fast lookup to prevent duplicate submissions

**Migration File:** `V1__create_leads_table.sql`

## Table: `audit_conversations`

Each time a lead starts an AI diagnostic session, one row is created here.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `UUID` | `PK, DEFAULT gen_random_uuid()` | |
| `lead_id` | `UUID` | `FK → leads(id), NOT NULL` | The lead who started this audit |
| `current_step` | `VARCHAR(50)` | `NOT NULL, DEFAULT 'INTRO'` | Current FSM state (AuditStep enum value) |
| `status` | `VARCHAR(20)` | `NOT NULL, DEFAULT 'ACTIVE'` | `ACTIVE`, `COMPLETED`, or `ABANDONED` |
| `started_at` | `TIMESTAMPTZ` | `NOT NULL, DEFAULT NOW()` | When the conversation was started |
| `completed_at` | `TIMESTAMPTZ` | nullable | Set when status becomes `COMPLETED` |

**Valid values for `current_step`:** `INTRO`, `TEAM_SIZE`, `TOOLS_USED`, `PAIN_POINTS`, `BUDGET`, `COMPLETE`
**Valid values for `status`:** `ACTIVE`, `COMPLETED`, `ABANDONED`

**Migration File:** `V2__create_audit_conversations_table.sql`

## Table: `conversation_messages`

Stores every single message in every conversation — both user messages and AI replies.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `UUID` | `PK, DEFAULT gen_random_uuid()` | |
| `conversation_id` | `UUID` | `FK → audit_conversations(id), NOT NULL` | Which conversation this belongs to |
| `role` | `VARCHAR(20)` | `NOT NULL` | `USER` or `ASSISTANT` |
| `content` | `TEXT` | `NOT NULL` | Full text of the message |
| `extracted_data` | `JSONB` | nullable | Structured data the AI extracted from user message |
| `step_number` | `INTEGER` | `NOT NULL` | FSM step this message belongs to (0–5) |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL, DEFAULT NOW()` | |

**`extracted_data` Examples by Step:**
```json
// After INTRO step
{ "businessName": "Sharma Textiles", "industry": "Fabric Manufacturing" }

// After TEAM_SIZE step
{ "teamSize": 12 }

// After TOOLS_USED step
{ "tools": ["WhatsApp", "Excel", "Tally"] }

// After PAIN_POINTS step
{ "painPoints": ["No CRM", "Manual invoicing", "Order tracking on WhatsApp"] }

// After BUDGET step
{ "monthlyBudget": "₹15,000" }
```

**Indexes:**
- `idx_messages_conversation` on `(conversation_id)` — fast retrieval of all messages in a conversation

**Migration File:** `V3__create_conversation_messages_table.sql`

## Table: `audit_reports`

The final AI-generated business audit report. One per completed conversation.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `UUID` | `PK, DEFAULT gen_random_uuid()` | |
| `conversation_id` | `UUID` | `FK → audit_conversations(id), UNIQUE, NOT NULL` | UNIQUE enforces one report per conversation |
| `health_score` | `INTEGER` | `NOT NULL` | Business health score 0–100 |
| `vulnerabilities` | `JSONB` | `NOT NULL` | Array of identified problem strings |
| `revenue_gap_estimate` | `VARCHAR(100)` | nullable | e.g., `"₹28,000/month"` |
| `recommendations` | `JSONB` | `NOT NULL` | Array of actionable recommendation strings |
| `generated_at` | `TIMESTAMPTZ` | `NOT NULL, DEFAULT NOW()` | When the report was generated |

**Migration File:** `V4__create_audit_reports_table.sql`

## Why JSONB for arrays?
PostgreSQL's `JSONB` type is used to store arrays like `vulnerabilities` and `recommendations` instead of creating separate join tables. This is because:
1. These arrays are always read together with the report — never queried independently.
2. The size and structure can vary per conversation.
3. JSONB is indexable and fully queryable if needed in the future.
4. It avoids unnecessary table complexity for Phase B.

## Why UUID for all PKs?
1. **Security**: Integer IDs reveal how many records exist (`/leads/1`, `/leads/2`...). UUIDs don't.
2. **Distributed systems**: If we ever shard or merge databases, UUID IDs never collide.
3. **Client-side generation**: Frontend can generate a UUID before sending a request if needed.
